## What We're Building

Not a new plan — a critique of an existing one. Revision 2 of the Yellow Jules integration plan is unusually rigorous: it already resolves most tactical questions (SDK-vs-REST fallback trigger, hidden-retry disablement, cache ownership, autonomy defaults, four-PR-plus-engine-milestone sequencing) with explicit, evidence-tagged stances. The brainstorm's job is therefore not to re-derive those decisions but to (a) verify a few of the plan's own unverified facts against the live repo/registry, (b) surface gaps the plan doesn't see about itself, and (c) offer alternative shapes for the parts that are genuinely still open.

Repo grounding performed during this session:

- **`@google/jules-sdk@0.2.0` is real and resolvable on the npm registry** (`npm view @google/jules-sdk dist-tags version` returned `{"latest": "0.2.0", "version": "0.2.0"}` from this environment). This settles the plan's single biggest unverified fact (§6.2/§16: "did not download/verify the npm tarball" / "Verify the candidate published SDK package"). It does not verify the tarball's exports, ESM shape, or integrity hash — the plan's requirement to pin by hash after inspecting the actual tarball still stands.
- **No prior Jules work exists anywhere in this repo.** `rg -i jules` across tracked files and `plans/` returns nothing. Confirms the plan's own "no matches" claim and that PR1 starts clean.
- **The repo convention for a pre-implementation plan doc is top-level `plans/`, not `docs/plans/`** (e.g., `plans/complete/stacked-pr-provider-abstraction.md` (archived), `plans/thermonuclear-review-integration.md`, `plans/specs/*.md`). The plan's own kickoff prompt (§16) already targets `plans/yellow-jules-integration.md` — consistent, not a gap.
- **The provider-router (`remote-agent-provider-state.js`) is data-driven** (a frozen array + object keyed by provider id), so adding `jules` there is additive, not a switch-statement rewrite — lower risk than the pre-pass's general "closed-enumeration" warning suggested for this file specifically.
- **`plugins/yellow-linear/commands/linear/delegate.md` and `plugins/yellow-core/commands/setup/all.md` are NOT data-driven — they hard-code `cursor`/`devin` in prose, regexes, and branch logic** at many sites: `delegate.md` lines 3–4 (description, `argument-hint`), 41 (`--provider` validator: "exactly `cursor` or `devin`"), 202–203 (`READY_CURSOR`/`READY_DEVIN` → provider mapping), 388 (`PROVIDER="cursor"` default), 566–569 and 625–628 (per-provider dispatch/status branches), 666 (per-provider error table); `setup/all.md` lines 106-127 (credential probes), 289 (plugin enumeration list), 480–516 (per-provider READY/PARTIAL sections), 722–723 and 858–886 (status table rows, setup command list). **This is the concrete site list for the plan's own §7 requirement** ("Cover two- and three-provider conflicts... all existing Cursor/Devin behavior") — worth pasting into the PR2 description as a literal checklist so nothing gets missed.
- **`scripts/validate-provider-groups.js` is generic** (parses the catalog + a `provider-table:start/end` marker block, not literal `cursor`/`devin` string checks), so it will catch a missing/malformed Jules provider-table entry automatically — but it cannot catch a missed prose/regex update in `delegate.md` or `setup/all.md` above, because those aren't inside its scope (confirmed via the script's own "SCOPE BOUNDARY" comment: it validates static declaration shape, not the runtime dispatch prose).
- **`yellow-devin` is a live REST-first precedent already in this repo** (`curl` against `api.devin.ai/v3/`, org/enterprise scope fallback, service-user token auth) sitting next to `yellow-cursor`'s SDK-first precedent. A REST-first Jules implementation would not be introducing an unprecedented pattern — it would be following the *other* existing remote-agent provider's shape, not just Cursor's.
- Per the learnings pre-pass (below), the Codex-distribution pipeline has silent CI gaps until a plugin's `targets.codex.enabled` flips to `true` — directly relevant to §12/PR3's Codex-enablement step.

1. **Pre-implementation REST-provider security audit** (`docs/solutions/security-issues/yellow-devin-plugin-security-audit.md`) — a prior threat model for a REST-transport remote-agent provider identified three load-bearing patterns that would transfer directly to a REST-first Jules implementation: (a) session/resource-ID format validation before every API call (reject path-traversal and injection characters), (b) token-leakage hardening in error paths (never `curl -v`/`--trace`; strip `Bearer [^ ]*` from logged errors), and (c) fallback-chain correctness — a documented post-ship bug showed a 403→enterprise-endpoint fallback that failed to re-capture `curl_exit`/`http_status`/`body` after the second call, silently swallowing the fallback's real error.

This repo's own memory records this recurring at least four times (#676, #677, #695, #697). Directly motivates the file/line checklist captured above.

## Why This Approach

The plan's decision to keep `yellow-jules` a sibling plugin (not a Jules Fleet fork, not a second goal controller) is sound and matches the repo's existing `remote-agent` capability-group pattern exactly — this session found no reason to challenge that top-level shape. The genuine open territory is narrower than the plan's length suggests:

1. **The plan never states why Jules, given the group is exactly-one-enabled and Cursor is already preferred.** An "experimental/manual" third provider only runs when a user has deliberately disabled Cursor. If the real motivation is Jules's *asynchronous, long-running* execution model (which the v0 interactive CLI explicitly does not exploit — §5 forbids blocking waits, and §9 requires bounded human-in-the-loop polling), the plan may be building the wrong-shaped v0: scaffolding for the deferred goal-engine milestone dressed as a Cursor-parity CLI. This is worth confirming before PR1, not after.
2. **The plan's own constraints mean it uses almost none of the SDK's value-add.** §5 bans `run()`, `all()`, `result()`, `ask()`, `waitFor()`; §6.3 disables the SDK's hidden retries; §6.4 isolates/neutralizes its cache; §6.1 asserts every flag manually rather than trusting SDK defaults. What's left is essentially "typed request/response shapes over an HTTP call, plus an official ESM build to vendor." That is close to what a REST-first adapter would deliver directly, without inheriting the SDK's retry/cache side effects that the plan otherwise spends most of §6 fighting. Given `yellow-devin` already proves a REST-first remote-agent provider works in this repo, REST-first is a legitimate peer approach, not merely the plan's contingency fallback.
3. **Artifact-first patch staging fights the vendor's native grain.** Jules natively opens PRs; the plan suppresses that (`autoPr: false`, `AUTOMATION_MODE_UNSPECIFIED`) and builds a parallel patch-staging/collection pipeline (§11) specifically so the existing stack-provider workflow stays authoritative. That's defensible, but it's also the single largest chunk of net-new plumbing in the plan (journal, artifact provenance, staging worktree, base-mismatch checks) for behavior the vendor would give away for free if allowed to land its own PR and be reviewed by the existing `/review:pr` tooling like any other external contribution.

Recommendation: **keep the sibling-plugin architecture (confirmed), but resolve #1 explicitly before PR1, and treat #2/#3 as a real fork in the road rather than assuming the SDK+artifact-first path by default.** The three approaches below make that fork concrete.

### Approach A: Ship the plan as written, hardened with this session's gaps

Keep SDK-first with the adapter interface, artifact-first delivery, and the full four-PR-plus-engine-milestone sequence exactly as revision 2 specifies. Fold in this session's findings: the literal enumeration-site checklist for PR2, a `codex.enabled` pre/post snapshot baseline before PR3, and an explicit answer to "why Jules" recorded in PR1's contract doc.

**Pros:** No re-litigation of an already-thorough plan; every stance in revision 2 is preserved; SDK typing reduces hand-rolled request/response shape risk if the tarball inspection in PR1 goes cleanly.
**Cons:** Carries the SDK's retry/cache-neutralization tax (a large fraction of §6's test surface exists solely to defeat SDK defaults); artifact-first staging is the most net-new code of any option; does not resolve the unstated "why Jules now" premise.
**Best when:** The premise is confirmed (async/unattended execution is the actual near-term goal, and the interactive v0 is accepted as deliberate scaffolding toward it) and the team wants the SDK's typed surface enough to pay the neutralization cost.

### Approach B: REST-first, PR-native, two release boundaries

Same sibling plugin, same adapter interface (so this is a transport choice, not an architecture change — consistent with the plan's own §1 stance that a broken SDK path "triggers an adapter/transport decision first, not abandonment"). Implement directly against the documented REST endpoints (`jules.google/docs/api/reference/*`) the way `yellow-devin` does, using the security-audit patterns from the pre-pass (ID validation, redaction, fallback re-capture) instead of inheriting SDK retry/cache behavior to defeat. Accept vendor-created PRs as an external artifact reviewed through existing `/review:pr` tooling rather than building a separate patch-staging pipeline; add stack-provider adoption as a later, explicitly-approved policy once that path is proven. Collapse PR1+PR2 into one contract-and-implementation boundary (the plan's own PR1 is docs-only and has no runtime code to gate); keep supervision/Codex as PR3.

**Pros:** No SDK packaging/ESM verification risk at all; no retry/cache neutralization test layer; reuses a pattern already proven in this repo (`yellow-devin`); less net-new plumbing than artifact-first staging; fewer release boundaries.
**Cons:** Loses the SDK's typed request/response shapes (hand-rolled validation instead); still needs the explicit-flags/no-auto-PR discipline from §6.1, now enforced by hand rather than via typed `SessionConfig`; still needs the retry/backoff/deadline discipline of §6.3, just without an SDK default to fight.
**Best when:** The team weighs "less net-new code, proven local pattern" over "typed vendor SDK," and is comfortable accepting vendor PRs into the normal review flow rather than treating auto-PR as a policy deviation to suppress.

### Approach C: Validate the premise first, defer marketplace infra

Before any catalog registration, provider-router change, or Linear routing, run the plan's own §3-endorsed alternative — "an isolated capability experiment" via the upstream Jules MCP, or a single human-authorized SDK/REST smoke task in a throwaway repo — to answer "why Jules" concretely: is the value unattended async execution (which argues for waiting on the `yellow-goal` engine milestone before building a full sibling plugin), or is it parity with Cursor/Devin today (which argues for Approach A or B now)? Only then commit to A or B with the four-PR machinery.

**Pros:** Cheapest way to falsify the premise before investing in a full plugin; the plan already concedes MCP is "suitable for an isolated capability experiment"; avoids building marketplace infrastructure (catalog entry, provider-router changes, Linear routing, Codex exposure) for a provider that might turn out to only make sense after the goal engine lands.
**Cons:** Adds a step in front of PR1; the plan's evidence register already did most of this via source/doc inspection (J1–J9) — an experiment adds live-observation evidence but delays start; risks becoming an indefinite "one more spike" if not time-boxed.
**Best when:** There's real uncertainty about whether Jules's value is realized in v0's interactive/CLI form at all, versus only after the durable goal-engine milestone — which this session could not resolve from the document alone.

## Key Decisions

- **Chosen approach: A** (user decision, 2026-09-09). SDK-first with the adapter interface, artifact-first delivery, four PRs plus a separate engine milestone, plus this session's hardening: the enumeration-site checklist in PR2, the Codex snapshot baseline before PR3, and an explicit "why Jules" statement in PR1's contract doc.
- **Motivation: async/unattended execution** (user decision, 2026-09-09). v0's interactive CLI is scaffolding toward the `yellow-goal` engine milestone; Cursor/Devin parity is a side effect, not the goal.
- Sibling-plugin architecture, not a Jules Fleet fork or second goal controller — confirmed, not reopened by this session.
- `yellow-goal` engine integration stays a separate, explicitly-approved milestone — confirmed, not reopened.
- Transport: SDK-first per revision 2 (settled by the Approach A choice). REST-first remains the plan's own §1 contingency if PR1's tarball/ESM investigation fails, and the SDK-neutralization tax identified above is the accepted cost.
- Artifact-first patch staging stays (settled by the Approach A choice); vendor auto-PR remains suppressed so the stack-provider workflow is authoritative.
- PR2's description carries an enumeration-site checklist so `delegate.md` and `setup/all.md` updates are exhaustive, not best-effort. The authoritative site list is spec R23/R24 (which adds the classifier tooling argv slot, the tooling probe, the Step 2.5 state enumeration, and the marker block this section omits); the line numbers in this doc's grounding section are provisional at `6a0bcc87` and are re-anchored at implementation.
- Codex enablement (PR3) should baseline `tests/integration/generate-manifests-codex.test.ts` before flipping `targets.codex.enabled: true`, per the learnings pre-pass.
