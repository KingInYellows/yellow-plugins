## Overview

Add a new **opt-in, read-only** review persona — `thermonuclear-reviewer` — plus
a preloaded skill `yellow-thermonuclear-review` to `plugins/yellow-review`,
adapted from Cursor's MIT-licensed `thermo-nuclear-code-quality-review`. It
applies a deliberately more aggressive structural-quality rubric than the
everyday `maintainability-reviewer`: behaviour-preserving "code-judo"
restructurings, spaghetti condition growth, weak type/module boundaries,
misplaced ownership, and file-size threshold crossings.

It is **never auto-selected**. Repositories opt in through the existing
`reviewer_set.include` mechanism, so no new slash command and no new dispatch
branch are required.

A second PR exposes **only the skill** (not the whole review workflow) to the
Cursor and Codex distribution targets via the catalog generator.

## Problem Statement

### Current pain points

`yellow-review` ships 16 agents. The maintainability lane
(`maintainability-reviewer`, always-on, `sonnet`) is calibrated as an everyday
reviewer: premature abstraction, dead code, indirection, coupling, naming. It is
deliberately *not* aggressive — it must stay low-false-positive because it runs
on every PR.

There is no lane that asks the harder question: *is this the right structure at
all?* Nothing currently flags a feature scattered through unrelated shared
paths, several booleans forming an implicit invalid state machine, or a refactor
that relocates complexity without removing any concepts.

### Who benefits

Repositories that want a high-pressure architecture pass on specific PRs, opting
in per-project rather than paying opus/xhigh cost on every review.

### Why not the alternatives

| Rejected option | Reason |
|---|---|
| Fold into `maintainability-reviewer` | Destroys its calibration as the always-on low-FP lane, and conflicts with in-flight PR #748 which edits that file. |
| Import Cursor's whole `thermos` / `cursor-team-kit` plugin | Enormous surface for one rubric; duplicates orchestration we already have. |
| A separate `yellow-thermonuclear` plugin | Premature — one agent and one skill do not justify a 20th plugin. |
| Make it always-on | opus/xhigh on every PR is not justifiable, and it would flood reviews. |
| Let it perform refactors | It is a reviewer. Structural rewrites must never enter an automatic-fix lane. |

## Blockers and Key Decisions

### B1: The 1,000-line rule is not computable by the reviewer

The rule requires `base_line_count < 1000 && head_line_count > 1000`. Per F6 the
reviewer sees only a unified diff and can `Read` HEAD. Hunk headers cover changed
regions, not file totals. Reconstructing base by hand-summing every `+`/`-` line
per file is error-prone LLM arithmetic and must not be the specified mechanism.

**Resolution.** The orchestrator already has Bash and resolves `DIFF_BASE` in
Step 3a, and there is direct precedent for a per-persona extra block
(`project-standards-reviewer` receives `<standards-paths>`). PR 1 adds a small,
persona-scoped block appended **only** when `thermonuclear-reviewer` is in the
dispatched set:

```
<file-line-counts>
path/to/file.ts base=986 head=1034
</file-line-counts>
```

sourced from `git diff --numstat -z "$DIFF_BASE"...HEAD` (NUL-delimited, never
line-split) plus `git show "$DIFF_BASE:$path" | wc -l`, where `$path` is
validated (rejected if absolute, containing `..`, or resolving outside the
repo root) before being used in either command. Paths get the same
literal-delimiter substitution and XML escaping as the main diff before
entering the prompt.
If the block is absent or unparseable the reviewer **suppresses size-threshold
findings entirely** rather than guessing — fail-closed.

> **Research — this challenges the rule itself, not just its implementation.**
> The 1,000-line threshold is a **folk heuristic with no empirical support, and
> the best-designed study points the other way.** Yamashita et al., "Thresholds
> for Size and Complexity Metrics" (QRS 2016; 4,575 OSS Java projects + 205
> Avaya industrial projects, validated against defect data in Eclipse, Mylyn,
> NetBeans) found that while defect *probability* rises in the very-high-risk
> group, "**the defect density was uniformly lower in the very high-risk group of
> files**" — the same code in large files carried *fewer* defects than when
> spread across smaller ones. Their stated conclusion: size/complexity thresholds
> "have to be used **with caution if at all**," with the "immediate practical
> implication: the **redistribution of Java code into smaller and less complex
> files may be counterproductive**."
> **Scope caveat — read this before leaning on that conclusion.** The study is
> **Java-only by deliberate design**: the authors restricted it to Java "to
> control for language context… [excluding] the possibility that our results were
> affected by the thresholds potentially having opposite effects in different
> languages" (they also excluded projects under 200 files). This repo is
> TypeScript/shell/Markdown, so the defect-density reversal is **not established
> here** and the "splitting is counterproductive" half should be treated as
> suggestive, not settled. What *does* transfer is the methodological point
> below — threshold derivation is language-independent.
> The methodological fix is cheap: the state-of-the-art derivation (Alves et al.,
> replicated by Yamashita) sets thresholds as **percentiles of a benchmark
> distribution** (70th/80th/90th), never as absolute constants. Replace
> "crosses 1,000 lines" with either (a) a **repo-relative percentile** computed
> from this repo, or (b) a **delta rule** — "this diff pushed the file across the
> repo's 90th percentile." Both keep the idea and drop the unsupported constant.
> Whichever is chosen, any split recommendation should carry an explicit
> caveat that redistribution has *some* evidence against it (Java-only; see scope
> caveat above) — enough to warrant hedging the recommendation, not enough to
> suppress it.
> Related: Roehm et al. (SWQD 2019, 6,897 repos / 402M lines) found most
> maintainability folk hypotheses unsupported — but that result is about
> *project* size, not *file* size, so do not over-cite it here.
> Sources: posl.ait.kyushu-u.ac.jp/~kamei/publications/Yamashita_QRS2016.pdf ·
> arxiv.org/abs/1806.04556

> **Research:** Google's static-analysis programme (Sadowski et al., CACM 2018 /
> SWE-at-Google ch.20) gives the governing number: keep **effective false
> positives under 10%**, where a finding is an effective FP if the developer took
> **no positive action — even if the warning was technically correct**. That is
> precisely the failure mode of an aggressive structural reviewer, whose findings
> can be true and unwanted at once. Analyzers with high not-useful rates get
> disabled; trust, not accuracy, is the binding constraint.
> Anthropic's own managed Code Review is near-exact prior art for this design:
> parallel agents each hunting a *different* issue class, then a **verification
> step that checks candidates against actual code behaviour**, then

> inventing our own — nit volume caps ("report at most five, mention the rest as

> making the aggressive lane opt-in — direct support for the never-auto-selected

<!-- deepen-plan: external -->
> **Research:** The three-tier split is well supported, and the real risk is
> **false assurance rather than flakiness**. Miller (Anthropic), "Adding Error
> Bars to Evals" (arXiv:2411.00640) implies a nine-fixture suite is
> statistically incapable of detecting small regressions: it recommends ~**1,000
> questions** for good power, and warns that **clustered standard errors can
> exceed naive ones by >3×** when items share structure — which fixtures drawn
> from the same PR do. It also gives the highest-leverage cheap technique:
> **analyse paired differences** (same fixtures, both variants) rather than
> comparing point estimates. State this limitation in the plan explicitly so the
> fixture suite is never read as a regression gate.
> A failure mode a fixture suite cannot defend against: **vendor-side model
> upgrades shift scores overnight**, breaking a threshold gate for reasons
> outside the repo. Practitioner reports describe score drift with no code change
> (0.84 → 0.79 on rerun) leading teams to disable the gate entirely.
> Therefore: keep score-based comparison **out** of CI permanently; if any
> fixture behaviour is ever promoted to blocking, make it **binary and
> high-margin** (must-catch on a seeded regression / must-not-flag on a clean
> diff), run k times with a majority requirement — binary assertions with wide
> margins do not flap the way a 0.79-vs-0.80 threshold does.
> Precedent: Anthropic's managed Code Review check run "always completes with a
> **neutral** conclusion so it never blocks merging," exposing a machine-readable
> severity count for teams that want to build their own gate downstream — the
> same defer-to-aggregator posture this plan takes.
> Sources: arxiv.org/abs/2411.00640 · code.claude.com/docs/en/code-review ·
> braintrust.dev/articles/what-is-llm-as-a-judge

# Recommendation

Add Cursor’s rubric to **`plugins/yellow-review` as an opt-in structural-quality reviewer**.

I would **not**:

* Fold it into the existing `maintainability-reviewer`.
* Import Cursor’s entire `thermos` or `cursor-team-kit` plugin.
* Create a separate `yellow-thermos` plugin yet.
* Make it an always-on reviewer.
* Allow it to automatically perform large architectural refactors.

Your current `yellow-review` already provides adaptive orchestration, correctness, security, maintainability, adversarial review, testing analysis, simplification, structured findings, and stack workflows. The existing maintainability reviewer is an everyday, calibrated reviewer for premature abstraction, dead code, indirection, coupling, and naming.

Cursor’s rubric is deliberately more aggressive. It seeks “code-judo” restructurings, rejects ad hoc branching growth, challenges type and module boundaries, watches for files crossing 1,000 lines, and holds code to a stricter approval standard than mere behavioral correctness.

The resulting architecture should be:

```text

        │

        │                  │
        │                  └── opt-in from /review:pr
        │
        ├── Cursor: generated allowlisted skill
        │
        └── Codex: generated allowlisted skill
```

| Free-form review comments                     | Convert to compact-return JSON                                                                    |

### Evidence requirements

Every finding should satisfy all of the following:

1. **Identify the structural regression**, not merely say that code is complicated.
2. **Point to changed code** with a repository-relative path and line.
3. **Describe the simpler model**, ownership boundary, or control flow.
4. **State what behavior remains unchanged** under the proposed restructuring.
5. **Verify claimed canonical helpers or abstractions actually exist** before recommending reuse.
6. **Avoid domain-complexity false positives** where the implementation is complex because the real business domain is complex.

For the 1,000-line rule, require:

```text
base line count < 1000
head line count > 1000
file is not generated, vendored, or a lockfile
new content has a coherent extractable responsibility
```

A file that was already 1,400 lines and gains a localized five-line fix should not automatically receive a threshold finding. Likewise, crossing 1,000 lines should ordinarily be P2 rather than P1 unless the resulting structure creates a concrete high-impact engineering risk.

### Scope boundary with existing reviewers

The new reviewer should not report these by themselves:

```text
Poor variable naming
An isolated unused helper
Ordinary missing tests
A straightforward correctness bug
A known security vulnerability
A local retry/timeout problem
Formatting or style preferences
```

Those already have owners in your review system.

It should report:

```text
A new feature scattered through unrelated shared paths
Several booleans creating an implicit, invalid state machine
A refactor that moves complexity but does not remove any concepts
A wrapper hierarchy that obscures a direct data flow
A cast-heavy boundary concealing the real invariant
A duplicate helper when a verified canonical implementation exists
An orchestration sequence that can leave related state half-applied
A large-file crossing where one cohesive module can clearly be extracted
```
